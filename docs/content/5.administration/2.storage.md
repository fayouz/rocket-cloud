## Quota et taille des fichiers

| Variable | Rôle | Défaut |
|---|---|---|
| `CLOUD_DEFAULT_QUOTA` | Espace disponible pour chaque utilisateur, en octets | `10737418240` (10 Go) |
| `CLOUD_MAX_FILE_SIZE` | Taille maximale d'un fichier, en octets | `536870912` (512 Mo) |

Le quota est le même pour tous les utilisateurs. Un dépôt qui le dépasserait est refusé (`413`), comme un fichier trop gros ; l'utilisateur voit son espace utilisé dans **Mes fichiers** et sur le tableau de bord.

::note
PHP limite aussi la taille des envois : l'image de l'API accepte jusqu'à 512 Mo (`upload_max_filesize` et `post_max_size` dans `backend/docker/php.ini`). Pour aller au-delà, augmentez ces valeurs, et celles du proxy HTTP placé devant Rocket Cloud le cas échéant (`client_max_body_size` pour nginx).
::

## Dossier des données

Le contenu des fichiers est stocké sur le disque, dans `DATA_DIR/files/` (volume `app_data` dans Docker), sous un **nom opaque** tiré de l'identifiant du fichier. Les noms, les dossiers et les métadonnées sont en base.

- Sauvegardez **ensemble** la base de données et le dossier des données : l'un sans l'autre ne permet pas de restaurer les fichiers.
- L'API et le worker doivent partager ce dossier.
- Le tableau de bord signale un dossier non accessible en écriture (service **Stockage**).

Rocket Cloud ne déduplique pas les fichiers : chaque dépôt occupe sa place, même à l'identique. L'empreinte SHA-256 de chaque fichier est toutefois conservée (`sha256`).

## Confidentialité

Chaque espace est **privé**, y compris vis-à-vis des administrateurs :

- l'interface et l'API ne listent que les dossiers, fichiers et liens de partage de l'utilisateur connecté (ou de celui qu'une application impersonne) ;
- un administrateur voit sur le [tableau de bord](/administration/dashboard) des chiffres de la plateforme, pas les fichiers des autres ;
- une application n'accède aux fichiers d'un utilisateur qu'en l'impersonnant, et jamais avec le rôle administrateur.

Désactiver un utilisateur (page **Utilisateurs**, ou disparition de l'annuaire LDAP) conserve ses fichiers, mais rend ses liens de partage inutilisables. Supprimer un utilisateur supprime ses dossiers, ses fichiers et ses liens en base ; le contenu de ses fichiers reste en revanche dans le dossier des données. Préférez la désactivation, ou demandez-lui de vider son espace avant.

## Notifications par email

Quand un utilisateur partage un fichier avec des destinataires, Rocket Cloud leur envoie le lien par **Rocket Mailer**, la brique d'envoi d'emails du Middleware Rocket. Rocket Cloud y est une **application externe** qui envoie au nom de l'utilisateur qui partage (impersonation).

::steps{level="3"}

### Déclarer Rocket Cloud dans Rocket Mailer

Dans Rocket Mailer, **Administration → Applications → Nouvelle application** : nom « Rocket Cloud », avec l'option **Peut agir en tant qu'utilisateur**. Notez le jeton (`rma_…`), affiché une seule fois, et complétez les réglages d'envoi que Rocket Mailer demande pour une application.

### Configurer Rocket Cloud

```bash [.env]
ROCKET_MAILER_URL=https://mailer.exemple.com   # l'API de Rocket Mailer, vue depuis le worker
ROCKET_MAILER_TOKEN=rma_…
FRONTEND_URL=https://cloud.exemple.com         # base des liens envoyés : <FRONTEND_URL>/s/<jeton>
```

Redémarrez l'API et le worker.

### Vérifier

Le tableau de bord affiche le service **Rocket Mailer (notifications)** : le worker appelle `GET /api/me` avec le jeton toutes les 5 minutes, ou tout de suite avec **Vérifier maintenant**, et affiche le nom de l'application reconnue.

::

### Dans la suite Rocket

En mode suite (`ROCKET_AUTH_URL` renseignée), Rocket Cloud n'a pas besoin de jeton statique : il demande à Rocket Auth un jeton d'accès pour Rocket Mailer (flux **identifiants client**, audience `rocket-mailer`, valable 5 minutes et gardé en cache), et Rocket Mailer le rattache à l'application liée au client `rocket-cloud`.

1. Dans **Rocket Auth**, le client `rocket-cloud` a le flux **Identifiants client** (c'est le cas des clients de démo).
2. Dans **Rocket Mailer**, **Administration → Applications** : l'application « Rocket Cloud », avec **Peut agir en tant qu'utilisateur** et le **Client Rocket Auth** `rocket-cloud`.
3. Dans **Rocket Cloud**, seule `ROCKET_MAILER_URL` est nécessaire (`ROCKET_MAILER_AUDIENCE` si le client ID de Rocket Mailer n'est pas `rocket-mailer`).

Pendant la transition, gardez `ROCKET_MAILER_TOKEN` : si Rocket Mailer refuse le jeton de Rocket Auth (`401`, application pas encore liée), Rocket Cloud réessaie avec le jeton statique. Le tableau de bord indique « (jeton Rocket Auth) » quand la vérification passe par la suite.

Les utilisateurs de Rocket Cloud doivent aussi exister dans Rocket Mailer, avec la même adresse : c'est le cas quand les deux partagent le même annuaire LDAP ou la même authentification unique (Rocket Auth).

L'email contient le nom de l'élément partagé, le message éventuel, un bouton **Ouvrir le partage**, la date d'expiration et, si le lien est protégé, un rappel que le mot de passe est communiqué séparément : il n'est **jamais** dans l'email.

L'envoi est fait par le worker, une seule fois. Son résultat s'affiche dans **Mes partages** : envoyé, ou l'erreur (Rocket Mailer non configuré, jeton refusé, utilisateur inconnu…). En cas d'échec, le lien reste valable et l'utilisateur peut le transmettre lui-même.

Si `ROCKET_MAILER_URL` est vide, ou `ROCKET_MAILER_TOKEN` hors du mode suite, les liens se créent normalement, sans email, et le service apparaît comme **Désactivé** sur le tableau de bord.
